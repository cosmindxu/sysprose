# Formal verification for Sysprose — obligations, proofs and evidence, command line first

## Summary

You get a verification lane that starts with the cheapest honest answer and only then reaches for a solver. `contracts` reads every requirement as the assume/guarantee pair the standard defines and the bundled library carries structurally (`Requirements::RequirementCheck` owns an `assumptions` and a `constraints` ConstraintUsage; the body `allTrue(assumptions()) implies allTrue(constraints())` is the shipped library's wording (`Systems Library/Requirements.sysml`); Part 1 §9.2.14.2.8 spells it without the call parentheses — the shipped graph carries no expression for it, so `contracts` reads the two features, not that formula). `obligations` turns that into a worklist: what must be shown, over which axioms, and — the part that matters — which relations the existing unit gates refuse and why. `verify --engine literal` then discharges what it can with no solver installed at all, saying only "holds at the model's values". Adding `z3-solver` upgrades the same command to `--engine smt`, where a discharge means the negation came back UNSAT and a refutation comes with a witness that has been re-evaluated in-process before it is printed.

Verdicts are written back through **two channels, both tool-local**: a `verdict` string on the unbound `metadata RequirementMetadata` carrier this tool defines (`src/semantics/requirements.ts`:23), and an evidence record as §7.27 metadata in a `@SysproseVerification::Evidence` carrier naming the tool, its version, the bound, and a digest of the model it was computed over. The one standard slot this lane writes is `@VerificationMethod { kind = analyze; }` on the case. Later phases add requirement-set consistency with a named conflicting subset, compositional refinement in Cimatti's normal form, exact bounds, bounded state-machine reachability, minimal cut sets from contract-failure injection, and export/import for z3, cvc5, OCRA, nuXmv and Lean.

The order is deliberate: six commits to a running `obligations` + `verify --engine literal` on `examples/uav-isr.sysml` and `examples/vehicle.sysml` — three of them paying off prerequisite defects in the mapper, the serializer and the validation rules, and one shipping the keyword reader, before anything reads what they produce; three more to the SMT engine behind the same unit gates that `checkConstraints` already applies, pinned by a differential test and a relation census that together make the word "proved" safe to print. What this can say: *proved* (negation UNSAT under a satisfiable axiom set, non-vacuous), *refuted with witness*, *design-admitted* (a refutation obtained by freeing a value the model states), *holds at the model's values*, *holds structurally*, *holds within bound*, *vacuous*, *inconclusive*.

**What it can never say — the MUST-NEVER list, in one place.**

1. Never *verified*, *correct*, *safe*, *deadlock-free* or *realizable*, anywhere, about anything.
2. Never *proved* from a bounded run, a point evaluation, or a solver that was not installed.
3. Never *proved* when the axiom set was not shown satisfiable, when the solver returned unknown, or when any relation in the obligation's own body was refused by the unit gates.
4. Never *proved* or *refuted* for an obligation carrying a free variable unbounded on either side — the tool derives no domain axioms from ISQ quantity kinds and does not know that a power or a mass is non-negative, so a witness outside the physical domain is not a counterexample and the obligation is `inconclusive`.
5. Never *refined* while any obligation is undecided, and **never *refined* when the antecedent of obligation (3) or (4) is unsatisfiable** — that is `vacuous`.
6. Never `verdict = "pass"` in the file for a claim that is not `proved`; `refuted` writes `fail`, and every other claim writes `inconclusive`, with the finer claim in the evidence carrier.
7. Never "the standard's own vocabulary" for the verdict facet: `RequirementMetadata` occurs 0 times in the specification, and the standard's own slot — `VerificationCase::verdict : VerdictKind {redefines result}` — is one this tool does not bind.
8. Never a green build under `--engine auto` or `--engine smt` when the solver was absent.
9. Never a *pass* on a partial exploration, and never a liveness verdict without a named fairness assumption.
10. Never *no cut set* over a contract set whose baseline obligation was vacuous, and never absence of a single point of failure when any order-1 check was undecided.
11. Never a third-party `#keyword` described as standard, and never an absent annotation read as a fact.

The exit contract is stated once, exhaustively, in `VERIFY_EXIT_CODES` (§2), and this is the single most important design decision here: **a missing solver never produces a proof, and never a green build under `--engine auto` or `--engine smt`.**

### 1.1 Four prerequisite defect families, each measured, not assumed

These are behaviour changes to shipped round-trip semantics. **D1, D2 and D4 are paid off first, in their own commits**, because everything downstream reads what they produce. **D3 is not fixed at all** — ids stay fresh per load, no commit in this plan touches `src/core/ids.ts`, and every digest and every SMT assertion name canonicalises to qualified names instead (commit 3). So this is three prerequisite *fixes* plus one worked-around defect, and the keyword reader of commit 2d is a **gap** (§1 *Lacks* item 9), not a defect payment.

- **D1 — clause-body drop.** `mapRequirementClause` (`src/text/langium/map-to-model.ts`:2089) reads `node.kind`, `node.name`, `node.specializations` and `node.expr` — **never `node.body` or `node.members`**, for any clause kind. Probed: `objective { doc /* … */ assume constraint { armed == true } require constraint { altitude > 0.0 } }` maps to a `ConstraintUsage` with `attrs.requirementRole = 'objective'` and **zero children**, and serialises as `objective;`. The doc, the assumption and the guarantee are destroyed, and the deletion is **idempotent**, so nothing downstream notices. It is wider than the nested `verify` the first draft reported: `actor a { doc }`, `stakeholder h { doc }` and `frame f { doc }` lose their bodies too, and `require constraint bound { doc /* keep me */ s.x < 10.0 }` loses **both** the doc and the `constraint` keyword. What goes with them is the standard's own home for a behaviour precondition and postcondition — `CaseBodyItem → ObjectiveMember → ObjectiveRequirementUsage : RequirementUsage`, typed by `Cases::Case::obj : RequirementCheck[1]`.
- **D2 — the serializer omits `constraint`.** `requirementClauseLine` (`src/text/serializer.ts`:701) drops the keyword, emitting `require bound { x < 10.0 }` and `assume { … }`. Under the published grammar (spec line 12009), `RequirementConstraintUsage`'s first alternative is an `OwnedReferenceSubsetting` — a **reference** to an existing `bound`, not a declaration of one — and `require { … }`, with neither `constraint` nor a `#keyword`, matches **no** alternative at all; `AssertConstraintUsage` is the same shape. Sysprose round-trips its own output only because its own grammar makes `constraint` optional — `sysml.langium`:285, verbatim: `| kind=('require' | 'assume' | 'assert') ('constraint' | 'requirement')? (name=Name)?`. (Line 282 is the *actor / stakeholder / objective / frame / verify* alternative, which carries no `constraint` at all.) This is a conformance defect in the **writer**, with a corpus-wide byte diff.
- **D3 — fresh UUIDs on every load.** `src/core/ids.ts` → `crypto.randomUUID`; verified, two loads of the same text give different ids. **Any digest or named SMT assertion keyed on element ids is unstable across runs.** Ids must be canonicalised to qualified names before hashing or naming.
- **D4 — `validation/requirement-subject` fires on an inherited subject.** `requirement r : Def;` warns even where the subject comes from the definition. It must resolve through `effectiveFeatures`.

D1 and D2 must not be split from each other: the round-trip test that proves either one needs the other. Together with D4's behaviour change and the vocabulary package, that is why commit 2 becomes four commits — mandatory, not stylistic.

## 2. The verification story

A requirement enters as prose plus an `assume`/`require` pair on a subject. It leaves as a verdict facet in the file with an evidence record beside it. Between those two points sit three engines and one agent loop.

**The engines.**

- **Structural / SMT (z3 WASM, in-process).** Decides quantifier-free arithmetic over feature values: is this requirement set satisfiable at all (unsat core when not); does this `require` hold for *every* value the model admits (negation UNSAT); what is the tightest bound on a measure. It sits **behind** the existing unit gates, so what z3 sees is already dimensionally sound and every relation the gates refuse is listed, never dropped.
- **Contracts / composition (same solver, different obligations).** Do the component contracts, together with the equalities the model actually states, entail the system contract; is every component assumption discharged by its siblings; does a derived requirement refine the one it derives from; which combinations of contract failures break the top requirement.
- **Behavioural / bounded model checking (pure TS, plus optional z3 and nuXmv).** Which states are reachable; which transitions can never fire; where does the simulator silently pick one of several enabled transitions; do the **safety** patterns hold on every reachable configuration.

**The agent loop around them.** `contracts` and `obligations` say what exists and what must be shown. `prompts --element R` surfaces the `#prompt` guidance the engineer wrote. `property-draft` returns a FRETish skeleton plus a data dictionary of every name, type and unit legal in the subject's scope. `property-check` refuses a clause outside the encodable fragment, or one that does not parse, does not resolve, clashes dimensionally or is trivially true on its own — and prints a back-translation with a fixed line saying the tool did **not** check that the clause means what the prose meant. `verify --record` produces the evidence; `evidence-attach` writes it into the file; `evidence-status` says which records went stale after an edit.

### The exit contract, stated once and exhaustively

Single-sourced in `VERIFY_EXIT_CODES` in `scripts/lib/sysprose-spec.ts`, beside `EXIT_CODES`:20 and `CHECK_EXIT_CODES`:34, with the same style of comment explaining why it is a third contract. `CommandSpec` gains an `exitContract: 'report' | 'verify'` field so `renderCommandUsage` and the reference generator quote the right one.

| Exit | When, exhaustively |
|---|---|
| **0** | Every obligation discharged non-vacuously **by the engine that was asked for**. Under `--engine literal`, `holds-at-values` counts as discharged. Under `--engine smt` and `--engine auto` it does not. |
| **1** | At least one obligation **refuted with every feature at its model value** (`--free none`, the default). Nothing else is exit 1. |
| **2** | Usage · IO · degraded model · **any** inconclusive — `verification/timeout`, `verification/unsupported-construct`, `verification/not-evaluable` (unknown), witness not confirmed, `verification/vacuous`, `verification/method-not-performed` — · **solver absent** (`verification/tool-absent`) · **`design-admitted`** — a refutation obtained under `--free`, which is a design the model admits, not a violation of it. |

**`--engine auto` resolves to `smt` when `loadZ3()` returns a backend, and otherwise emits `verification/tool-absent` for every obligation ⇒ inconclusive ⇒ exit 2.** It never silently downgrades to `literal`. A point evaluation is only ever green when it was asked for by name.

**`--allow-inconclusive` is scoped.** It lowers 2 → 0 **only** for obligations that are *undecided* — `verification/timeout` and `verification/unsupported-construct`. It never lowers `verification/tool-absent`, never lowers `verification/vacuous`, never lowers `verification/method-not-performed`, never lowers `design-admitted`, and never wins over a violation: exit 1 beats it. The scope is stated over **codes**, not over prose, so every commit gate in §4 can be read against this list. The summary line still prints the inconclusive count first, and names which inconclusives were forgiven. There is **no** `--allow-unperformed`: forgiving an unjudged verification method would be a separate flag and a separate decision, and this plan does not ship one (§8 decision 1).

**`vacuous` is an inconclusive under every `exitContract: 'verify'` command, and it always exits 2.** That holds for `verify`, `consistency`, `refine`, `bounds`, `check-behaviour` and `fault-tree` alike — one claim word, one exit code, no per-command exception. `--strict-vacuity` does **not** change the exit code; it promotes the vacuity row from an info line to `verification/vacuous-property` as an error in the report and in `npm run check`, so a vacuity that was previously easy to scroll past becomes a finding. Vacuity is this plan's one declared deviation from the standard (§6, §8.4.17), and no flag launders it back to green.

### 2.1 The annotation vocabulary — what the standard already says, and the one gap this plan ships

A practitioner's four-keyword vocabulary — `#precondition`, `#postcondition`, `#Exception`, `#Observable` — was put to this plan as a possible source of proof obligations. Three of the four questions it asks are good ones. Only two of the four keywords survive contact with the specification, and **only one of those ships here**.

**The rule this section applies.** If SysML v2 already expresses a facet, the plan uses the standard construct and ships no keyword. A keyword is warranted only where the specification is silent, and then it ships exactly as `#prompt` does — a `metadata def` in a package Sysprose ships as text, plus a user-defined keyword (§7.27.1, §7.27.4). Nothing is invented, and no third-party vocabulary is ever described as standard.

| Facet | Slide keyword | Does SysML v2 express it? | The standard construct | Decision |
|---|---|---|---|---|
| **BEFORE** | `#precondition` | **Yes, three ways** | `assume constraint` in a requirement body (`RequirementKind = 'assume' { kind = 'assumption' }`, Part 1 §8.2.2.21.1); `objective { assume constraint { … } }` on any case — `ObjectiveRequirementUsage : RequirementUsage = UsageExtensionKeyword* ConstraintUsageDeclaration RequirementBody` (grammar, spec line 12110), typed by `Cases::Case::obj : RequirementCheck[1]`; `guard` on a transition (`TransitionPerformances::TransitionPerformance::guard`) | **Reject the keyword.** Read the standard construct: a `#precondition` keyword would be redundant syntax for something the specification names three ways. |
| **AFTER** | `#postcondition` | **Yes** | `require constraint`; `objective { require constraint { … } }`, whose subject **defaults** to the case's result per the shipped `Systems Library/Cases.sysml` — `objective obj : RequirementCheck[1] { subject subj default Case::result; }` — and is **bound** to the case subject per `VerificationCases.sysml` (`subject subj = VerificationCase::subj;` — a binding, not a default, per §3.2's own rule). That is the standard's way of saying the objective is checked against what the case produced | **Reject the keyword.** `require constraint` and `objective { require constraint { … } }` already carry it, and the objective's subject already resolves to the case result; a `#postcondition` keyword would be redundant syntax for a construct the specification names in the requirement body and on every case. |
| **VALENCE** | `#Exception` | **No** | `grep -oi "exception[a-z]*"` over the whole of Part 1 returns **nothing** — 0 occurrences. `VerificationCases::VerdictKind::fail` is a case **result**, not a model-authored classification of an outcome; `RiskMetadata::Risk` is probability and impact, not valence. The specification's own §7.27.4 example is `#situation occurrence def Failure;` (line 10318) — the standard *demonstrates* a user-defined failure marker | **Adopt**, as `#exceptional` over a shipped `metadata def`. Ships at commit 2d. |
| **VISIBILITY** | `#Observable` | **No** | "observable" occurs exactly twice in Part 1 (lines 9425, 23632), both inside one narrative use-case sentence. A sentence, not a construct. `out` port direction and `flow` say what crosses an interface, not which *step* is published; `VerificationMethodKind` sits on the case, not the step | **The gap is real, but HOLD.** See below. |

**Why `#observable` is held.** A shipped `metadata def` that the tool writes into user files is a **compatibility commitment**: withdrawing it later turns a user's file into `verification/keyword-names-nothing`. `#observable` discharges no obligation — its whole output would be one info verdict and an atom filter — and nothing in this plan depends on it. So commit 2d ships the **reader**, the resolver and the foreign-alias table, which are what make any vocabulary legible, and ships exactly one keyword through them: `#exceptional`, which earns its keep because the obligation it synthesises is `absence × globally`, one of the four patterns the bad-prefix engine can actually decide (§3.8). `#observable` is revisited at Checkpoint B, when a shipped example either needs it or does not.

**On preconditions for a plain behaviour, the standard has an idiom and it is not a keyword.** `ActionBodyItem` admits no `RequirementConstraintMember`, so `assume` / `require` are not legal in an `action def` body. What the specification does instead is name an invariant: `inv precondition { … }` appears **five times** in the KerML Kernel Function Library — for example `VectorFunctions`: `inv precondition { v.dimension == w.dimension }` — and the single occurrence of the word anywhere in SysML Part 1 is the abstract-syntax constraint name `positionTimePrecondition`. In SysML notation that idiom is `assert constraint precondition { … }`, which parses in Sysprose today with zero diagnostics. The three standard answers for a behaviour precondition are therefore a named `assert constraint` as an axiom, a `guard` on the incoming transition, or a `requirement` whose `subject` is the behaviour, tied by `satisfy` — and `contracts` reads all three.

**Why this changes the plan at all: the standard construct is unreadable today.** That is defect family D1 (§1.1). Before commit 2a, `objective { … }` is silently deleted on save — which is both why no keyword is needed for BEFORE/AFTER and why nothing downstream could have read one anyway.

**What the mechanism costs, measured.** `#precondition`, `#postcondition`, `#Exception`, `#Observable`, a qualified `#SysproseVerification::exceptional` and even a misspelt `#precondtion` all parse with zero diagnostics on an `action def`, an action usage, a `use case def`, a state usage, a port usage and an attribute usage; each lands in `attrs.metadata` **as written**; each round-trips. A model annotated with somebody else's vocabulary is therefore already read and preserved losslessly, and nothing in this plan may break that. A plain `package SysproseVerification { metadata def <exceptional> ExceptionalOutcome; }` round-trips too, so `STATEMENT_KIND_LIBRARY`'s shape is the one to copy. Do **not** use the `SemanticMetadata` shape `ParametersOfInterestMetadata` uses for `<moe>`/`<mop>`: `:>> baseType = xs meta SysML::Usage;` produces three `ref/unresolved-specialization` warnings today and the serializer rewrites `SysML::Usage` to `SysML::Systems::Usage`. Do **not** use `metadata X about Y;` — it does not parse. `@Def { attribute … = "…"; }` inside a body does round-trip, and is the carrier §3.10 depends on.

**One caveat on round-tripping, corrected.** The keyword round trip is **idempotent from the second save**, not byte-identical from arbitrary input: measured, `#exceptional\n    part def Abort;` comes back as `#exceptional part def Abort;`. Every test in this plan asserts idempotence from the second save, and the interoperability ratchet (§5) is written against that, not against byte-identity.

### 3.0 How the table is read: subcommand names, and how a `REF` resolves

**Subcommand names are single tokens.** `findCommand` (`scripts/lib/sysprose-spec.ts`:221) matches `argv[0]` against `COMMANDS` by exact name, which is why the eight shipped names are single tokens and `where-used` is hyphenated. Every new row here is therefore hyphenated too — `property-draft`, `property-check`, `evidence-status`, `evidence-attach`, `evidence-detach`, `certificate-import`, `check-behaviour`, `fault-tree` — and the CLI column above quotes what a reader can actually type. Nothing in this plan adds two-token group dispatch.

**How a `REF` resolves, stated once because six new commands take one.** `--element`, `--subject`, `--case` and `--measure` all accept **either a qualified name (`P::uav::endurance`) or a short id (`R-UAV-001`)**, resolved by the same resolver `prompts --element` and `where-used --element` already use — one resolver, extended, never a second. Resolution order: exact qualified name, then exact `declaredShortName`, then an exact `declaredName` that is unique in the model. **On multiple matches the command exits 2** and prints every match with its qualified name; it never picks one. On no match it exits 2 with the nearest-name suggestions the property gates already compute. A `REF` naming a library element is refused. The behaviour is pinned by an L7 CLI case per new command, because six commands sharing an undefined convention is how two of them end up with different ones.

### 3.1 `contracts` — the inventory

**In-process API.** `contractsOf(model): Contract[]` and `contractOf(model, reqId)` in `src/semantics/contracts.ts`; `contractReport(model)` in **`src/api/verification.ts`**, alongside `obligationsReport` and re-exported from `src/api/index.ts` — it is the sibling of `constraintReport` (`src/api/analytics.ts`:1514) in shape, not in location. Each contract: `{id, qualifiedName, shortId, subject:{name, typeRef}, assumptions[], guarantees[], satisfiedBy[], derivedFrom[], refinedBy[], verifiedBy[], variables:[{path, featureId, role:'input'|'output'|'parameter'|'derived', unit, siFactor}], fragment:'qf-lra'|'qf-nra'|'temporal'|'unsupported', unsupported:[{expression, reason}], keywords[]}`.

**The fragment rule, stated because the flagship example turns on it.** `fragment` is `qf-lra` **only when every relation is linear after literal substitution**. Freeing any feature that appears as a divisor or inside a product promotes the obligation to `qf-nra`, and the report names the free variable that caused the promotion. On `examples/uav-isr.sysml`, freeing `cruisePower` makes `endurance = battery.capacity * usableEnergyFraction / cruisePower` a division by a variable, so the endurance obligation is **QF_NRA**, not QF_LRA — z3 5.0.0 rejects it outright under `(set-logic QF_LRA)`.

**Constructs read.** `RequirementDefinition`/`RequirementUsage`; owned children with `attrs.requirementRole ∈ {subject, assume, require, objective}` and `attrs.expression`; **case objectives** — a `CaseDefinition`/`CaseUsage`, `UseCaseDefinition`/`UseCaseUsage` or `VerificationCaseDefinition`/`VerificationCaseUsage` whose `objective` clause carries `assume`/`require` children is a contract on a behaviour, with the subject **defaulting** to `Case::result` per `Cases.sysml` (`subject subj default Case::result;`) and **bound** to the case subject per `VerificationCases.sysml` (`subject subj = VerificationCase::subj;` — a binding, not a default, per §3.2's own rule) (readable only after commit 2a); `Satisfy` (source = part, target = requirement), `Derive` (source = **original**, target = **derived**), `Refine`, `Verify` (source = case, target = requirement). Port `attrs.direction` classifies variables as inputs vs outputs. Library rows and `#prose`/`#prompt` statements are dropped the way `constraintReport` does (which filters `attrs.isLibrary`); `contracts` uses the stronger `isUserElement`, which also drops implicit elements and elements whose owner is implicit — and the digest of §3.10 must therefore be written `model.toJSONWhere((el) => isUserElement(model, el))`, since `toJSONWhere` takes a one-argument predicate.

**Where the four orientations were measured, and where they were not.** `Satisfy` is measured on both shipped examples (`examples/uav-isr.sysml`:140-141, `examples/vehicle.sysml`:62). **Neither shipped example declares a `verify`, a `derive`, a `refine` or an `objective`** — `examples/uav-isr.sysml` contains none of them — so the `Verify`, `Derive` and `Refine` orientations are measured on hand-built probe models, and commit 2c re-measures each against its own case. Any statement in this document that an orientation was "measured by probe" means exactly that, and never that it was read off a model the reader has in front of them.

**Written back.** Nothing. New diagnostics under the single new `DiagnosticSource` `'verification'`: `verification/unsupported-expression` (info), `verification/contract-no-guarantee` (info — assumptions with nothing to prove), `verification/nonstandard-clause-location` (info — `assume`/`require` in an `action def` body, which Sysprose accepts and the standard's `ActionBodyItem` does not admit), `verification/foreign-keyword` (info), `verification/keyword-names-nothing` (info).

**Verdict semantics.** MAY say: "N contract(s) on M subject(s); K guarantee(s) in QF_LRA, J in QF_NRA, U unsupported"; and, for a requirement with prose but no constraint body, "no formal clause". MUST NEVER say satisfied, proved, consistent or anything about truth — this command reports structure. An empty inventory on a model that has requirements is stated explicitly, never rendered as zero problems. MUST NEVER present an objective assumption as a system requirement, and MUST NEVER report an objective as empty when the mapper is the reason — the pre-2a behaviour is an L8 case so it cannot regress silently.

**Literature.** `benveniste-2015-theory` (what a contract is), `cofer-2012` (contracts on an architecture — target AADL/Lustre, see §7), `westman-2013` (ISO 26262 safety goals and FSRs as contracts), `almeida-2024` (which KerML feature/value readings are settled and which are not), `omg-sysml-2.0-part1-2026` §7.20–§7.21 (the constructs themselves).

**App affordance.** A Contracts table view, **added** in the closing commit; the CLI ships first.

### 3.2 `obligations` — the worklist

**In-process API.** `obligationsOf(model, {scopeId?}): Obligation[]` in `src/semantics/obligations.ts`; `obligationsReport(model)` in `src/api/verification.ts`. Each obligation: `{requirement, shortId, subject, role:'axiom'|'premise'|'obligation', node: ExprNode (unit literals lowered to SI), vars, sortPerVar:'Real'|'Int'|'Bool', encodable: true | {reason, detail}, nonlinear: boolean, verifiedBy[], method, evidence[], status, provenance?}`.

**The role map, complete.** `require` → obligation. `assume` → premise. `assert constraint` → axiom (this maps to a `ConstraintUsage` with `attrs.requirementRole = 'assert'`, **not** a distinct metaclass). Feature-value expressions and `bind` edges → axioms; a `=` feature value is a binding in KerML, not a default. And the row the first draft was missing: **a plain `constraint c { … }` — no role, not `assert` — is an OBLIGATION, not an axiom.** It is what `checkConstraints` judges, so it must be what the SMT engine judges, or the two surfaces cannot be compared at all. Filing it as an axiom would make one false plain constraint turn `check(A)` UNSAT and downgrade every genuine violation in the run to `inconclusive` — exit 2 by default, and exit 0 under an unscoped `--allow-inconclusive`.

**Therefore the axiom set is exactly:** feature-value bindings, `bind` equalities, and `assert constraint` bodies. Nothing else.

**Encodability is the same gate the numeric surface applies**, because it calls the same functions: `parseRelationBody`, `lowerUnitLiterals`, `substituteLiterals`, `relationScope`, `scaleOfRelation`, `relationRefused`, `storageScaleOf`, `nodeDimension` — today module-private in `src/semantics/solver.ts` at lines 385–1249, lifted in commit 1.

**`--from-keywords` (off by default).** A clause read through a foreign keyword — somebody else's `#precondition` or `#postcondition` — contributes a premise or a guarantee **only** under this flag. Every such row prints the keyword it came from and the words "third-party spelling; not SysML v2, not a Sysprose keyword", and the flag is recorded in the evidence record so a proof that leaned on a vocabulary Sysprose did not define cannot be replayed as though the model had said it.

**This command reports storage state, never truth.** `open`, `no-formal-clause` and `not-encodable` are structural readings; **`discharged` and `stale` are read back from an attached evidence record, never computed here** — `discharged` means a record exists whose claim is `proved` and whose `modelVersion.graph` still matches, `stale` means one exists and it does not. There is no `vacuous` row: vacuity is an SMT decision (§3.4 step (2)), and no TypeScript mechanism in this command could produce it, so claiming it here would be exactly the defect this plan exists to prevent — a verdict word its declared engine cannot decide.

**`--missing` — defined here because §6 calls it the deliverable that measures encodability.** It restricts the worklist to the obligations that have **no current evidence record and no formal clause to encode** — the `no-formal-clause` and `not-encodable` rows — and prints their histogram. It is the "what would this lane not decide on your model?" mode, and it needs no solver.

**Written back.** Nothing. This is the standard's `RequirementCheck` decomposition made visible.

**Verdict semantics.** MAY say per relation: "encodable (linear real arithmetic)", "encodable (nonlinear — NRA, may time out)", "not encodable: `dT == t2 - t1` on °C is offset-scale arithmetic". MUST NEVER say anything about truth. A relation the gates refuse is **listed with its reason**, never omitted — the `checkConstraintsNumeric` rule (`src/semantics/solver.ts`:2447), carried forward. A requirement carrying a hand-written `verdict = "pass"` facet with no evidence record is reported as **"claimed pass, no evidence"**. MUST NEVER contribute a keyword-derived premise or guarantee without printing the keyword on that line.

**Literature.** `cofer-miller-2014` (objective-by-objective evidence), `rushby-1993` ch. 2–3 (what a proof certifies, and that its assumptions must be listed with it), `mavridou-2020` (verdicts mapped back to the requirements they concern), `almeida-2024`.

### 3.3 `property-draft` / `property-check` — authoring under gates

**In-process API.** `src/api/property.ts`. `propertyDraft(model, reqId)` emits the **three mandatory** FRETish fields — `component`, `shall`, `response` — as the encodable skeleton, plus a **data dictionary** from `featureIdsFor(model, subjectId)` (`src/semantics/evaluate-model.ts`:67) giving every legal name with its type, unit, dimension claim and literal value, plus every `#prompt` that reaches the requirement or its subject type, verbatim, plus example clause shapes generated from the dictionary. The other three fields — `scope`, `condition`, `timing` — are emitted as **commented guidance** marked `fragment: temporal — not encodable by any in-process engine; export-only (§3.11)`, with the reason printed. `mavridou-2026` is explicit that only three of the six are mandatory and that an omitted `timing` defaults to *eventually*, which is a liveness reading no engine in phases 0–3 can discharge.

`propertyCheck(model, reqId, clause)` runs **gate 0 and then four judging gates**:

- **(0) encodable fragment.** A clause whose `scope` is not `global` or whose `timing` is not the default is **refused at gate 0**, naming the field — `verification/temporal-field-unencodable`. It is not "accepted with a gap": nothing downstream can decide it.
- **(1)** `parseExpr` succeeds.
- **(2)** every `ref` path resolves in the subject scope, with nearest-name suggestions in `expected`.
- **(3)** dimensions agree via `evaluateConstraintQuantityDetailed` on a transient constraint over `model.clone()` — never on the caller's model.
- **(4) syntactic non-triviality** — the clause is neither valid nor unsatisfiable **on its own**: clause SAT **and** ¬clause SAT under z3, **with no axioms asserted**; with no solver, the gate reports "non-triviality not checked: z3 absent". Note the scope: a clause that is trivially true once the model's feature values are pinned is **not** caught here — `uav.mtow <= 25.0 [kg]` passes gate 4 even though `uav.mtow = 18.5 [kg]` is a literal in the file. That is what `verify`'s tautology check (step 3) and the vacuity report are for, and the limit is recorded in the §6 limits register.

It returns a back-translation of the AST into structured English and the insertion `range` inside the requirement body.

**Constructs read.** `#prompt` statements via `promptsFor` (`src/api/analytics.ts`:1059), the requirement `doc` via `requirementStatement`, the `subject` clause, ISQ typing and unit literals, existing `assume` clauses.

**Written back.** Nothing — the tool tells, the agent edits, the existing write → `npm run check` → repair loop applies. Optionally the FRETish fields travel with the clause as a `@SysproseVerification::Property { … }` carrier (§7.27), so the structured English that produced the formula stays beside it.

**Verdict semantics.** MAY say: "accepted: parses, resolves 3/3 names, dimensionally consistent, non-trivial on its own"; "refused at gate 0: `scope = after` is temporal — no in-process engine decides it; export it (§3.11) or restate the clause globally"; "refused: `endurance` does not resolve in the scope of `uav` — did you mean `uav.endurance`?"; "accepted with a gap: non-triviality not checked (z3 absent)". MUST NEVER say the clause is a correct formalisation of the prose. Every report ends with the same fixed line: **"meaning is not checked; read the back-translation."**

**Literature.** `mavridou-2026` + `fret-fretish-semantics-2019` (the six fields, and which three are mandatory), `ma-2026` (data dictionary and template before the LLM), `cosler-2023` (sub-translation traceability → the back-translation, and why `p`/`q`/`r`/`s` stay separate attributes), `danso-2026` (syntax is easy, semantics is hard — the gates are the answer to that bar), `andresel-2026` (lightweight consistency check on generated properties), `post-menzel-2011` (pattern-grammar expressiveness on industrial requirements).

**App affordance.** A "Draft property" action on a requirement in the Properties panel; deferred.

### 3.4 `verify` — discharge, and verification cases get a computed verdict

**In-process API.** `verifyModel(model, opts): Promise<VerifyReport>` in `src/api/verification.ts`, over two engines.

`src/semantics/engines/literal.ts` wraps `checkConstraints` and `evaluateConstraintQuantityDetailed`: it evaluates the assumptions first, so a pass is either "assumptions hold at these values" or, if an assumption is false, `vacuous at values` → inconclusive. **`checkConstraints` has a third status** — `'unknown'` (`src/semantics/evaluate-model.ts`:184) — and it is neither a pass nor a fail: it maps to `inconclusive: not evaluable at the model's values`, exit 2. It is handled explicitly in the differential gate (§5), because it is exactly where two engines are most likely to differ and exactly the case §1's own warning is about — a constraint that silently disappears reads as one that holds.

`src/semantics/engines/smt.ts` runs, per obligation *O* with premises *P* under axioms *A*: **(0)** once per run, `check(A)` — if UNSAT, every obligation is `inconclusive: axioms inconsistent (core …)`, because a proof from a contradiction is void; **(1)** `check(A ∧ P ∧ ¬O)` — UNSAT ⇒ proved, SAT ⇒ refuted with witness; **(2)** `check(A ∧ P)` — UNSAT ⇒ `vacuous`; **(3)** `check(¬O)` alone — UNSAT ⇒ `tautology: true`, still proved but flagged.

**Free variables must be two-sided.** `verification/free-variable-unbounded` is **emitted and BLOCKING**: an obligation with a free variable unbounded on either side is `inconclusive: freed feature X is unbounded below/above; a witness outside the physical domain is not a counterexample`, never `refuted`. This is not a hint. It is the rule that stops the flagship example printing a fabricated counterexample: encoded exactly as §3.2 and commit 4 specify, with `cruisePower` freed and only an upper premise, z3 returns **sat with `cruisePower = -1 W`** and `endurance = -1843200 s`, and the in-process re-evaluation gate of §5 *confirms* that arithmetic — so it would print as a genuine refutation of a requirement nothing is wrong with. The premise must be two-sided (`uav.cruisePower >= 100.0 [W] and uav.cruisePower <= 600.0 [W]`) before "proved" is available.

**`--engine auto`.** Resolves to `smt` when `loadZ3()` returns a backend; otherwise every obligation is `verification/tool-absent` ⇒ inconclusive ⇒ exit 2. There is no silent fallback to `literal`.

`runVerificationCases(model, opts)` in `src/semantics/verify.ts` dispatches each `VerificationCaseDefinition`/`VerificationCaseUsage`, resolving verified requirements through `Verify` relationships **and** — after commit 2a — through `objective { verify R; }` members. The verdict follows the library's `PassIf`: `pass` iff every verified obligation is proved and non-vacuous; `fail` iff one is refuted at the model's values; `inconclusive` otherwise; `error` when the backend threw.

**Method gating is the honesty rule.** `VerificationMethod` carries `kind : VerificationMethodKind [1..*]`, so a case may legitimately say `kind = (analyze, test)`. A case whose `kind` list contains `analyze`, or which specifies no method, is judged on the analyze part; any other kind present is reported `not performed: method is test/demo/inspect`. A case with no `analyze` in its list is **not judged**: "inconclusive: method is test — this tool performs analysis only", **exit 2**, never exit 1 — an unjudged case is not a refutation.

**Constructs read.** Everything `obligations` gathers, plus `verification def`/`verification` usages, `subject` clauses, `objective { verify R; }`, `verify R by V;`, and `@VerificationCases::VerificationMethod { kind = …; }` metadata.

**Written back (with `--record` then `evidence-attach`) — two channels, both TOOL-LOCAL, and the report says so.**

- The `verdict` string goes on the existing `metadata RequirementMetadata` carrier via `setRequirementAttr`. That carrier is an **unbound tag this tool defines, not a standard element**: `RequirementMetadata` has **0 occurrences** in the specification, which has only `DerivedRequirementMetadata` / `OriginalRequirementMetadata`, and `src/semantics/requirements.ts`:23 states plainly that the identifier resolves to nothing and that the value is stored as a quoted string. Its value list mirrors the library `VerdictKind` literals; it is not a `VerdictKind` reference.
- The evidence goes in a `@SysproseVerification::Evidence` §7.27 carrier, one per obligation.
- The standard's own verdict slot is `VerificationCase::verdict : VerdictKind {redefines result}`, and **this tool does not bind it**. That is recorded in `docs/CONFORMANCE.md`, not glossed here.
- `@VerificationMethod { kind = analyze; }` on the case **is** standard.

**The verdict facet is written only for two claims.** `proved` ⇒ `pass`; `refuted` at the model's values ⇒ `fail`. `holds-at-values`, `holds-structurally`, `holds-within-bound`, `design-admitted`, `vacuous` and `inconclusive` all write `verdict = "inconclusive"`, never `pass`; the finer claim lives in the evidence carrier and is what the Requirements table displays. A `verdict = "pass"` facet whose carrier's claim is not `proved` is `verification/verdict-overstates-evidence`.

**Verdict semantics.** MAY say: "proved: A ∧ ¬G unsat in z3-solver 5.2.0, **QF_NRA (nlsat)**, 4 fixed / 1 free, seed 0, timeout 5000 ms; assumptions satisfiable (witness cruisePower = 600 W)"; "refuted: witness cruisePower = 700 W ⇒ endurance 43.9 min (confirmed by re-evaluation)"; "design admitted by the model, not a violation of it: under `--free uav.cruisePower`, witness …"; "holds at the model's values (literal evaluation, 0 free variables)"; "vacuous: premises unsatisfiable under the axioms"; "inconclusive: unknown after 5000 ms"; "inconclusive: solver absent"; "inconclusive: not evaluable at the model's values". MUST NEVER say "verified", "correct" or "safe"; never "proved" from the literal engine; never "proved" when step (0) was not SAT, when z3 returned unknown, when any relation in the obligation's own body was refused, or when a free variable is unbounded on either side; never a pass without a satisfiable-assumptions witness; never a verdict for a verification method the tool did not perform; never call a refutation obtained under `--free` a violation of the model.

**Literature.** `dania-clavel-2016` (satisfiability checking of a constraint set in a solver — the negation-UNSAT formulation actually used here, and the many-sorted encoding that keeps undefinedness explicit), `cofer-2012` (the compositional obligations and why the system guarantee must follow from the component contracts; note its verification conditions are LTL goals discharged by k-induction over Lustre, **not** an SMT negation check), `kupferman-vardi-2003` (vacuity — steps 2 and 3), `filipovikj-2018` (SMT versus a model checker for requirement checks: same verdicts, far less model-building — the reason this engine comes first), `barbau-bock-2020` (SMT-LIB encoding conventions — for SysML **v1** blocks under the OBM stereotype; only the sort mapping and naming convention transfer), `cofer-miller-2014` (which verification objectives an analysis may claim credit for), `omg-sysml-2.0-part1-2026` §7.24 and §9.2.17 (VerificationCase, VerdictKind, PassIf, VerificationMethodKind).

**App affordance.** No solver in the browser in this plan (see §6); the Check panel shows a "prove in the terminal" hint with the exact command.

### 3.5 `consistency` — requirement-set satisfiability with a named conflicting subset

**In-process API.** `checkConsistency(model, opts)` in `src/semantics/consistency.ts`. Groups contracts by subject type via `conforms`, **releases every feature that carries a literal value** — keeping only the structural axioms, because a consistency question about a requirement set must not be answered by the values that happen to be in the file — asserts each requirement under a named tracking literal, and on UNSAT returns z3's unsat core as the conflicting requirement set with short ids. **`--with-values` re-pins those literals as axioms**, which is the mode the illustrative witness below was computed under. On SAT it returns a witness design point, re-evaluated in-process before it is printed.

**Written back.** `verification/inconsistent-requirements` (error, naming the core by element id and qualified name). No model mutation.

**Verdict semantics.** MAY say: "consistent (`--with-values`): witness mtow = 18.5 kg, cruisePower = 650 W (2 requirements, QF_LRA, 0 relations refused)"; "inconsistent: conflicting subset {R-UAV-002, `L8-consistency-conflict`::mtowFloor}"; "inconclusive: timeout". MUST NEVER say "consistent" without the refused count beside it; never call a core **minimal** unless `--minimize` ran its deletion loop to completion; never say **realizable** — that is reactive realizability and a different question, and the word is reserved by the claims guard. **Literature.** `post-hoenicke-2012` and `langenfeld-2019` (consistency of a requirement set as an engineering deliverable, at industrial scale), `filipovikj-2018`, `wu-farrell-2021` (MaxUSE: naming the conflicting constraints, and core minimisation — a UML/OCL target), `katis-2022` and `larraz-tinelli-2022` (realizability and unrealisable cores — cited as the boundary this stops at).

### 3.6 `refine` — composition and derivation as contract refinement

**In-process API.** `checkRefinement(model, opts)` in `src/semantics/refinement.ts`. For a system contract *C* = ⟨A, G⟩ on subject *S* with sub-contracts *C'* on the parts that satisfy them, the obligations are Cimatti's Theorem 1, **in normal form**, with `nf(C) = ¬A ∨ G`, preceded by a satisfiability precondition:

- **(0)** `check(A ∧ ⋀ nf(C′) ∧ γ)` — **UNSAT ⇒ every refinement obligation is `vacuous: the sub-contracts, the connections and the system assumption cannot hold together (core …)`, never `refined`.**
- **(3)** ⋀ nf(C′) ∧ γ ⊨ nf(C)
- **(4)** for each component *U*: A ∧ ⋀_{S′≠U} nf(C′) ∧ γ ⊨ A_U

Step (0) is not decoration. Sub-contracts C₁ = ⟨true, x > 10⟩ and C₂ = ⟨true, x < 5⟩ over one bind class, against a system contract ⟨true, x > 1000000⟩, make **the antecedent of obligation (3) unsatisfiable**, so (3) holds **vacuously** — without step (0) the tool prints "obligation (3) proved" for an architecture whose components cannot coexist and whose system guarantee is absurd. `fault-tree` inherits the same hole, and §3.9 closes it there.

The normal form is load-bearing too. With bare guarantees the static check is **unsound** under mutual support: take A₁ = G₂ = p and A₂ = G₁ = p with system contract ⟨true, p⟩; both obligations pass, yet an implementation with p false satisfies each component contract and breaks the system guarantee. `cimatti-2015` reduces to normal form precisely for the refinement checks, and so does this.

**γ — the connection assertion — comes from `bind`/`BindingConnector` edges AND from the directional item flows `propagateValues` already carries** (`src/semantics/connectors.ts`, step (b): "carry the source value forward to the target"), encoded as `target = source`. This is not a taste question: a γ that diverges from `propagateValues` would break commit 1's own stated gate, because `checkConstraints`, the app and every existing report already honour those flows, and an unencoded flow produces exactly the false negative §3.6's own worked example shows — "assumption of `flightComputer` not discharged: witness battery.powerOut.voltage = 0 V" is what you get when a flow that *does* carry the voltage was not encoded.

**Only a bare `connection` with no flow and no bind is refused.** It is listed under `notEncoded` with the hint *"a connection is not an equality; bind the attributes if they are one quantity."* An opt-in `--connections-as-equalities` exists for the OCRA reading, and when it is used the fact is printed on every verdict line. Counter-evidence, recorded rather than buried: `cristoforetti-2026` §4.1 — the one published SysML v2 → OCRA path — translates `connect` **and** `bind` alike into OCRA ports and connections, and Cimatti's γ is by definition the connection-and-delegation assertion. So the refusal here is a **stricter reading than the published path takes**, not a consensus. See §8 decision 2.

`--via derive|refine` reuses the same checker over `Derive`/`Refine` edges with the measured orientation: A_R ⊨ ⋀ A_D (the derived set assumes no more) and A_R ∧ ⋀ nf(G_D) ⊨ G_R.

**Written back.** `verification/refinement-failed` (warning, with witness), `verification/unconnected-assumption` (a part assumption over a port no connection reaches), `verification/derivation-not-refinement`, `verification/refinement-undecided`, `verification/contract-set-vacuous`. MUST NEVER say "the architecture satisfies its requirements"; never anything about ordering or time — this is the propositional/numeric shape, **not** OCRA's temporal refinement; never treat a bare `connect` as a value equality without the opt-in flag; never say "refined" while any obligation is undecided; **never say "refined" when the antecedent of (3) or (4) is unsatisfiable**.

### 3.7 `bounds` — the tightest value the model admits

**The question, stated precisely.** *What is the tightest value this measure can take under the model's **axioms** — feature values, `bind` equalities and `assert constraint` bodies — with `require` clauses **excluded**, because a requirement is what is being checked, not a fact?* This is why `--measure uav.mtow --free all` answers **unbounded above** even though `require constraint { uav.mtow <= 25.0 [kg] }` sits in the file. The exclusion is repeated on every verdict line, not only here; `--with-requirements` folds the `require` bodies in and says so.

**In-process API.** `boundsReport(model, {measure, sense, free, timeoutMs, withRequirements})` over z3's `Optimize`; objective in SI, result converted back to the feature's declared unit.

**Verdict semantics.** MAY say: "max mtow: unbounded above under the model's axioms (`require` clauses excluded)"; "max mtow = 25 kg exactly (linear optimum, `--with-requirements`), witness …"; "bound found: 47.3 min, optimality not established (nonlinear)". MUST NEVER present a non-optimal bound as the optimum; never fold a `require` body into the axiom set without saying so on the line. The report names both this and the heuristic coordinate-descent `optimize` in `src/semantics/solver.ts`, and says which is which.

**Literature.** `wu-farrell-2021` (the MaxSMT/νZ machinery; its own target is UML/OCL). `khelifati-2025` is *not* cited here — see §7.

### 3.8 `reach` and `check-behaviour` — bounded behaviour

**In-process API.** `src/semantics/mc/config.ts` exposes the pure one-step relation `enabledTransitions(model, cfg, input)` and `stepConfig(model, cfg, choice)`, factored out of the `fire` / `enterCascade` / `exitTo` / `chaseHierCompletion` closures inside `runHierRegion` (`src/semantics/execute.ts`). `exploreMachine` in `src/semantics/mc/explore.ts` does breadth-first exploration over hashed configurations, exploring **every** enabled transition where the interpreter takes the first. `checkProperty` in `src/semantics/mc/check.ts` decides **safety** patterns by bad-prefix search on that graph. **The engine is pure TypeScript throughout: no solver is in this lane.** z3 BMC / k-induction over guarded machines is a Checkpoint-D *decision*, not a capability this plan builds — the §3 table's Engine cell says `TS` for that reason, the way §3.12 handles `#observable`: designed, named, explicitly not shipped.

**The catalogue is split by class, because a bad-prefix search cannot refute a liveness property.**

- **Safety, decided by bad-prefix search:** `absence`, `universality`, `bounded-existence`, `precedence`.
- **Liveness, not decided in-process:** `existence`, `response`. Both report `inconclusive: liveness not checked in-process` until a lasso search lands and a fairness assumption is named. `vogel-2022` — this plan's own citation for the catalogue — is explicit that response is the path-formula exception, which is why it needs observer automata for it at all. A bad-prefix search over a finite configuration graph returns no bad prefix for `response`, and under a naïve "pass — holds on every reachable configuration" rule that would print a pass nothing earned.

**The demonstration on the shipped example is the nondeterminism finding, not a reachability count.** `FlightModes` in `examples/uav-isr.sysml` has four states and five **trigger-less** transitions — every one is a completion transition, and `autonomous` has two of them enabled at once (`→ manual` and `→ failsafe`). The interpreter's declaration-order tie-break means `failsafe` is never entered in simulation; `verification/nondeterministic-choice` is exactly the row that says so. Any report on this machine that shows trigger labels is fabricating them.

**Written back.** `verification/unreachable-state`, `verification/dead-transition`, `verification/deadlock`, `verification/nondeterministic-choice`, `verification/bound-exhausted`, `verification/behaviour-unsupported-construct`, `verification/vacuous-property`, `verification/malformed-property`, `verification/unknown-atom`. Properties live in the model as `@SysproseVerification::PropertyPattern { attribute pattern = "absence"; attribute scope = "globally"; attribute p = "state failsafe"; }` — §7.27 metadata, one attribute per field so the phrase-to-atom trace survives.

**Every behaviour report carries the semantic profile** — run-to-completion (chasing bounded at 64), priority (innermost substate first), history (shallow, by parent map), regions (interpreter concatenates, checker interleaves), deferred events (**none** — `triggerEquals` is an exact match, there is no event pool), time (discrete `after(n)`) — each with its provenance in `execute.ts`. `attrs.parallel` and `attrs.history` are reachable only through the API: `sysml.langium` has no keyword for them, so a machine using them is `verification/behaviour-unsupported-construct` with `exhaustive: false`, never reported as exhaustively explored.

**Unreachability may be stated unqualified only when four things hold at once:** the exploration was exhaustive, **no completion-chase bound was hit**, every trigger the machine names was offered, and no unsupported construct was raised. Otherwise it is `unreachable under {maxConfigs, maxDepth, maxCompletion 64, alphabet = the triggers the machine names}`, or, on any bound hit, suppressed entirely. *Implementation note:* `chaseHierCompletion` (`src/semantics/execute.ts`:1418) today exhausts its 64-step budget indistinguishably from reaching quiescence — no flag, no return value; commit 13 makes it return its budget state, and a budget hit sets `exhaustive:false` and empties the unreachable and dead lists exactly as a config-bound hit does.

**`--from-keywords`.** One `absence` × `globally` obligation per `#exceptional` element inside the machine named by `--element`, over the same configuration graph — see §3.12.

**Verdict semantics.** MAY say: "explored 41 configurations, exhaustive under {maxConfigs 10000, maxDepth 200, maxCompletion 64}"; "state `failsafe` unreachable (exhaustive)" — **only** under the four conditions above; "nondeterministic choice at `autonomous`: 2 completion transitions enabled, the simulator takes the first"; "pass — holds on every reachable configuration"; "fail — witness trace of 3 steps"; "bound exhausted after 10000 configurations: partial — the unreachable and dead lists are lower bounds and are NOT reported as findings"; "inconclusive: liveness not checked in-process". Reachability is always qualified "structurally" or "exhaustive under {bounds}". MUST NEVER say "verified", "deadlock-free", or "proved"; never a pass when `exhaustive` is false; never a liveness verdict without naming the fairness assumption.

**Literature.** `andre-2023` §2.6 (run-to-completion, substate priority, region conflicts — the profile's field list, and the survey's point that every published formalisation differs on exactly these), `omg-pssm-1.0-2019` Clause 9 (a UML/fUML oracle for the conformance scorecard), `vogel-2022` (the pattern × scope catalogue and the safety/liveness split — targeting UPPAAL timed automata), `kupferman-vardi-2003`, `peres-ghazel-2023` (what a trustworthy translation must establish), `chrszon-2025` (explicit-state scaling on a mode machine), `graics-2020`, `bouwman-2023` (fairness stated explicitly in an industrial case).

### 3.9 `fault-tree` — cut sets from contract-failure injection

**In-process API.** `computeFaultTree(model, opts)` in `src/semantics/fault-tree.ts`. Basic events are "sub-contract *i* not honoured". A set *F* is a cut set iff the normal-form obligation (3) fails when the guarantees in *F* are dropped. **A cut-set enumeration whose baseline obligation (3) was vacuous reports `inconclusive: contract set vacuous`, never `no cut set`** — obligation (3) can never fail from an UNSAT antecedent, so without this the tool prints "no cut set up to order 2" for a contract set that entails everything. Minimal cut sets are enumerated by increasing order up to `--max-order` (default 2), with supersets pruned; the count of checks run is reported. A `@SysproseVerification::FaultHypothesis { maxOrder = 2; }` carrier pins the bound in the model.

**The two safety lanes stay apart.** A `StateUsage` passed as `--element` is **refused** with a pointer to `check-behaviour --from-keywords`, never answered with an empty cut-set list; a contract-level top event whose requirement carries `#exceptional` is labelled as such and its cut sets are unchanged.

**Verdict semantics.** MAY say: "3 basic events; minimal cut sets up to order 2: {battery}, {radio, flightComputer}; 7 checks, all decided"; "no cut set up to order 2 — **higher orders not explored**"; "inconclusive: contract set vacuous". MUST NEVER claim absence of a single point of failure when any order-1 check was undecided; never call this a behavioural safety analysis — it is contract-level FTA, and the report says so.

**Literature.** `bozzano-2014` (fault trees from contract refinement; intermediate events are contract failures), `stewart-2021` (AGREE + Safety Annex + JKind over AADL: minimal cut sets by fault injection into contracts), `joshi-2006` (the founding MBSA statement), `sun-2022` (what counts as MBSA), `rauzy-2019` (why the safety model stays separate and synchronised — `FaultHypothesis` is that sync handle).

### 3.10 `evidence` — records bound to a model version and a tool version

**In-process API.** `src/api/evidence.ts`. `modelVersionOf(model, sourceText?)` returns `{graph, source?, library, sysprose}` where `graph` is SHA-256 over a canonical JSON of `model.toJSONWhere((el) => isUserElement(model, el))` with **elements sorted by qualified name and element ids replaced by qualified names** — because ids are fresh UUIDs on every load (D3), a digest over raw `SerializedModel` would change on a no-op reparse. `library` records the standard-library manifest count; `sysprose` records the package version plus the git sha when `git rev-parse` succeeds and **omits it otherwise, never inventing one**.

`obligationDigest` is SHA-256 over the **canonical `ExprNode`** of the obligation after unit lowering and literal substitution, with names canonicalised to qualified names — the same normal form the SMT-LIB exporter serialises. It is therefore defined and **required** from commit 3, before any SMT-LIB text exists, and is stable across engines.

`EvidenceRecord = {schema:'sysprose-evidence/1', obligation:{requirement, shortId, clause, obligationDigest}, verdict, claim, engine, tool:{name, version}, bound, witness?, certificate?, modelVersion, producedBy, flags}` with `claim ∈ {'proved', 'holds-at-values', 'holds-structurally', 'holds-within-bound', 'refuted', 'design-admitted', 'vacuous', 'inconclusive'}`, validated against `docs/schemas/evidence-record.schema.json` with `ajv` (already a dependency). `flags` records any option that changed what was proved — `--free`, `--connections-as-equalities`, `--from-keywords`, `--with-values`, `--with-requirements` — so a proof cannot be replayed as though the model had said something it did not.

`attachEvidence` writes a `@SysproseVerification::Evidence { … }` carrier under the requirement or the verification case, using the same `MetadataUsage` + `AttributeUsage` shape `setRequirementAttr` uses — a shape that parses today with zero diagnostics (probed) and round-trips through the serializer. The `SysproseVerification` package is the one created at commit 2d; commit 7 **extends** it with `Evidence` rather than declaring a second package. **Evidence accumulates**: a second run appends a record, a `fail` is never silently overwritten by a `pass`, and the diff of verdicts is printed.

New validation rule **`stale-evidence`** (warning, code `validation/stale-evidence`, rules 24 → 25) fires when a record's `modelVersion.graph` no longer matches, naming the changed slice via `impactClosure(model, reqId, 2)`. Attaching refuses under a faulted declaration, reusing `FAULTED_DECLARATION_REFUSAL`, and refuses to write a degraded model at all.

**What an external tool makes of this, stated because interoperability is the goal.** The verdict facet is `metadata RequirementMetadata { attribute verdict = "pass"; }` — an unbound tag holding a quoted string, where the standard has an enumeration on a different metaclass. A conforming SysML v2 reader is entitled to treat that line as an untyped annotation and ignore it; nothing obliges it to interpret the string. **The round trip that matters is Sysprose → someone else's tool, and it is untested**: this plan tests the write path only inside Sysprose. Commit 16 adds an interop probe through **`scripts/pilot-write-roundtrip.ts` against `SYSMLV2_PILOT_URL`** — the Intercax OMG pilot at `http://sysml2.intercax.com:9000` whose genuine cross-implementation exchange is already recorded in `docs/CONFORMANCE.md`:192-206 — pushing a model that carries a verdict facet and an `@SysproseVerification::Evidence` carrier, **not** `buildSampleModel`. It is emphatically **not** `scripts/pilot-roundtrip.ts`, which boots our own `createServer()` by default and is therefore the self round-trip, i.e. the very thing this paragraph says is not enough. The probe answers the **API/JSON path only**: what a foreign *textual* parser makes of the `.sysml` bytes is a different question and stays **untested** by this plan. The result is recorded in `docs/CONFORMANCE.md` as a measured fact, whatever it turns out to be. Until then no claim is made about what another tool reads.

**Verdict semantics.** MAY say: "current — model sha256:ab12… matches"; "stale — recorded at sha256:9f3c…, 3 elements changed in the requirement's slice — re-run `verify --record`"; "unrecorded — verdict facet present, no evidence". MUST NEVER upgrade a claim on display: a record whose claim is `holds-at-values` is never shown as *proved*; a stale record is never counted as discharged; a `verdict = "pass"` facet is never written for a claim that is not `proved`.

**Literature.** `clariso-2020` (incremental verification of UML/OCL: keep the witness and re-check it against the edited model before re-running the solver — that is what the stored witness is for, and what the digest indexes), `cofer-miller-2014` and `rushby-1993` (evidence must name tool, version and assumptions to be arguable), `newcombe-2014`. **On `seidewitz-2020`, corrected:** it is the metasemantic protocol for language *extension*, and measured, the words "metadata" and "annotation" occur **0 times** in it — so it does not support "tool-specific data belongs in metadata". That sentence is the specification's, and its citation is `omg-sysml-2.0-part1-2026` §7.27. `seidewitz-2020` is kept only for the extension discipline.

**App affordance.** The Requirements table gains verdict and evidence columns showing `current` / `stale` / `none`; a stale chip links to the changed slice. Read-only.

### 3.11 `export` and `certificate-import`

**In-process API.** `src/semantics/export/smt2.ts` emits the exact assertions the in-process solver saw, with `(set-info :source "sysprose <version> <digest>")`, **`:named` assertions keyed on qualified names, not element ids**, and one `(push) (assert (not G)) (check-sat) (get-unsat-core) (pop)` block per obligation. `export/ocra.ts` emits Othello (`COMPONENT` / `INTERFACE INPUT PORT` / `CONTRACT … assume: … guarantee:` / `REFINEMENT SUB` / `CONNECTION` / `CONTRACT c REFINEDBY …`). `export/smv.ts` emits one MODULE per machine with the state as an enumerated VAR and `next(state)` as a case over transitions. `export/lean.ts` emits a theorem skeleton with `#print axioms`; it imports `Mathlib.Data.Real.Basic` because core Lean has no `ℝ` — a "mathlib-free theorem over the reals" does not exist. `scripts/lib/external-tools.ts` (in `scripts/`, **never in `src/`**, so the browser bundle can never import `child_process`) discovers `z3`, `cvc5`, `ocra`, `nuXmv`, `lake` on PATH with a version probe.

`importCertificate` maps outcomes **strictly**: SMT-LIB `unsat` ⇒ proved; Lean requires build exit 0, no `sorry`, and `#print axioms ⊆ {propext, Classical.choice, Quot.sound}`; nuXmv `-bmc` imports as **"no violation within k"**, never as proved; a TLC or bounded run likewise. The obligation digest in the result must equal the one in the exported file or the import is refused (`verification/certificate-mismatch`).

**Verdict semantics.** MAY say: "exported 3 obligations, logic QF_NRA"; "cross-check: z3 5.0.0 (binary) agrees on 3/3"; "cross-check: DISAGREEMENT on R-UAV-001 (z3 unsat, cvc5 sat) — inconclusive, report it"; "inconclusive: cvc5 not installed; files written to out/ — run `cvc5 out/R-UAV-001.smt2`". MUST NEVER pick a winner on a disagreement; never translate a tool's log into "proved" unless the parsed line is that tool's own success verdict with the axiom set checked; never export an equality the model does not state; never silently truncate a model the exporter cannot express — it aborts naming the element.

**Literature.** `fbk-ocra-2.1.0-2021` (Othello grammar and commands), `cimatti-2013`, `cristoforetti-2026` (the one published SysML v2 → nuXmv/OCRA path, whose component mapping this follows), `barbau-bock-2020` (SMT-LIB as the interchange), `kausch-2025` (the deductive end), `lamport-2002` and `newcombe-2014` (what a bounded TLC run does and does not buy), `champion-2016` and `larraz-tinelli-2022` (CoCoSpec / Kind 2 for the reactive case), `gleirscher-marmsoler-2020` (tool trust and reproducibility as adoption blockers).

### 3.12 `#exceptional` and the keyword reader — the one facet the standard does not express that this plan ships

**The shipped vocabulary.** `SYSPROSE_VERIFICATION_LIBRARY` in `src/semantics/verification-vocabulary.ts`, written in the serializer's canonical shape so pasting it into a file and saving gives the bytes back unchanged:

```
package SysproseVerification {
    doc /* One annotation SysML v2 does not express, carried as a user-defined keyword over a metadata definition (SysML v2 7.27.1, 7.27.4). #exceptional says an outcome is a failure rather than an equally valid result. It is a Sysprose extension, not standard vocabulary. */
    metadata def <exceptional> ExceptionalOutcome;
}
```

Commit 7 extends this same package with `Evidence`, commit 12 with `FaultHypothesis` and commit 14 with `PropertyPattern`, rather than declaring more packages — so a model carrying a keyword and an evidence record declares one Sysprose package with one doc string.

**In-process API.** `src/semantics/keywords.ts`: `keywordsOf(model, id): Keyword[]` — the generalisation of the module-private reader at `src/semantics/statement-kind.ts`:135, which now consumes it — `resolveKeyword(model, keyword)` against `MetadataDefinition`s in scope, `hasKeyword(model, id, def)`, and `FOREIGN_KEYWORD_ALIASES`, a read-only table mapping `Exception`/`exception` → `exceptional`, `precondition` → the assumption role and `postcondition` → the guarantee role, each carrying the provenance string that gets printed.

**`#exceptional` — valence, and the obligation it creates.** On a `StateUsage`, `ActionUsage`, `UseCaseDefinition` or requirement it says: this outcome is a failure, not an equally valid result. Under `check-behaviour --from-keywords` each tagged element inside the machine named by `--element` becomes one **`absence` × `globally`** obligation — one of the four patterns the bad-prefix engine can actually decide (§3.8) — discharged by the same explicit-state explorer commit 13 builds, with no new engine. `reach` upgrades a tagged reachable state from an information row to `verification/exceptional-reachable`. It does **not** feed `fault-tree` (§3.9).

*Verdict semantics.* MAY say: "fail — `#exceptional` state `failsafe` is reachable; witness trace of 3 steps (exhaustive under {maxConfigs 10000, maxDepth 200, maxCompletion 64})"; "pass — no `#exceptional` configuration reachable, exhaustive under {…}"; "inconclusive: bound exhausted after 10000 configurations — **the absence claim is not made**"; "vacuous: the tagged state has no incoming transition". MUST NEVER say *safe*, *deadlock-free* or *verified*; never a pass when `exhaustive` is false; never count a tagged element outside the machine under `--element` as anything but an info row.

**Reading somebody else's vocabulary.** `contracts --keywords` inventories every prefix keyword with what it resolves to. A third-party `#Exception` produces the `#exceptional` obligation with `verification/foreign-keyword` (info) and the provenance printed on every line that used it. A third-party `#precondition` / `#postcondition` is read, listed, and contributes a premise or a guarantee **only** under `obligations --from-keywords`, which is off by default and recorded in the evidence record's `flags`. A keyword that names no `MetadataDefinition` in scope gets `verification/keyword-names-nothing` (info), emitted by `contracts --keywords` and **not** by `npm run check` — so the 24 validation rules, the `check` exit contract and the 81 fixtures are untouched.

*Verdict semantics for the inventory.* MAY say: "sysprose vocabulary: `#exceptional` on 1 element"; "third-party spelling: `#Exception` read as `SysproseVerification::exceptional` on `P::Abort` — **not SysML v2, not a Sysprose keyword**"; "names nothing: `#precondtion` on `P::Launch` resolves to no metadata definition in scope". MUST NEVER call a third-party keyword standard; never report a keyword as resolved when no `MetadataDefinition` in scope carries that name; never change an obligation set — this row is an inventory.

**`#observable` is HELD, and this is what holding means.** The gap is real — "observable" is a narrative word in Part 1, not a construct — and the design for it is written: a fifth, report-only gate on `property-check` that names the atoms a `demo` or `test` method could not witness, plus `--observable-only` on the data dictionary, plus a `verification/unobservable-atom` info row from the method gate. It is **not shipped**, because a `metadata def` the tool writes into user files is a compatibility commitment and this one discharges no obligation. Nothing in this plan depends on it. It is revisited at Checkpoint B; if a shipped example needs it, it is one commit against the reader that already exists.

## 5. Verification of the verifier

Eight mechanisms, each a test that fails loudly rather than a convention.

**Known-answer models.** An L8 suite corpus where the answer is known by construction: `mtow <= 25` with `mtow >= 30` is unsatisfiable with a two-element core; `x == x` is a tautology; `assume { x > 1 } require { x < 0 }` with axiom `x == 2` is vacuous; the two-component mutual-support model (A₁ = G₂ = p, A₂ = G₁ = p) must **fail** refinement under normal form; the contradictory-sibling model (C₁ = ⟨true, x > 10⟩, C₂ = ⟨true, x < 5⟩) must report **vacuous**, never refined and never "no cut set". Each case carries a golden verdict list, so a regression shows up as a diff, not as a wrong verdict nobody noticed.

**The differential gate (commit 5) — and what it does not prove.** With `--free none` the SMT engine answers the same question `checkConstraints` answers, so it must give the same answer on every encodable relation across the whole fixture corpus and both examples, including the `unknown` row and the strict-boundary rule fixed in `d568a1f`. But the gate compares **two consumers of one gatherer**: encodability "is the same gate the numeric surface applies, because it calls the same functions". A relation neither surface gathers — a construct the shared `parseRelationBody` drops, a feature chain that fails to resolve — is silently absent from both, both say "nothing to report", and the gate is green. **So the differential gate proves the two ENGINES agree on the relations the shared gatherer produced. It establishes nothing about a relation the gatherer dropped.** What earns *proved* is the negation-UNSAT under a satisfiable axiom set with a two-sided domain, **plus the relation census**.

**The relation census (commit 5).** Every constraint-bearing element in the user model is accounted for as encoded, refused-with-reason, or unsupported-with-code, and the counts are asserted equal to the element census. A case whose relation silently disappears fails the gate. This is the counter-measure to the blind spot above, and it is the one the first draft did not have.

**Witness re-evaluation.** Every SAT model is substituted back through `evaluate` with the same scope shape `checkConstraints` uses **before it is printed**. A witness the in-process evaluator does not confirm is reported as "inconclusive: witness not confirmed", never as a violation. This catches encoder bugs — a wrong unit factor, a sign error, a mis-scaled offset — in the direction that matters. Note its limit, exposed by the `cruisePower = -1 W` case: re-evaluation confirms *arithmetic*, not *physical admissibility*, which is why the unbounded-free-variable rule (§3.4) is a separate and blocking check.

**Mutation.** The behaviour differential test (commit 13) is a mutation test in disguise: the fold of `stepConfig` must reproduce `runStateMachine` exactly, so any change to the interpreter that the extracted step function does not mirror fails immediately. For the SMT layer, single-field mutations of a case (flip `>=` to `>` at an exact boundary; change `18.5` to `18.6`) must move the verdict in the expected direction and must move the model digest.

**Two-solver agreement, honestly scoped.** `export --format smt2 --cross-check <tool>` re-checks the exported obligation with a second engine. **On this machine `z3` 5.0.0 is on PATH and `cvc5` is not**: `which cvc5` finds nothing, and cvc5 1.3.4 exists only as a Python package in `~/.venvs/quant`, which a PATH-and-version probe cannot see. So the cross-check that runs today is the z3 binary against z3 WASM, which catches export defects but is **not** two independent engines; `--cross-check cvc5` reports `inconclusive: cvc5 not installed` with the command to run, and the two-engine claim is not made until a binary exists. A disagreement is always reported as **inconclusive with both verdicts named** — the tool never picks a winner. The export itself is tested to be what the in-process solver saw, by feeding it back through `fromString` and comparing verdicts, and to be byte-stable **across processes** (the test that catches any residual dependence on UUID element ids).

**The interoperability ratchet.** A case holding `#Exception`, `#Observable`, `#precondition`, `#postcondition`, a qualified `#SysproseVerification::exceptional` and a misspelt `#precondtion`, on six element kinds, must parse with zero diagnostics and round-trip **idempotently from the second save**, forever. It is what stops a future vocabulary commit from making Sysprose the only tool that can read its own files.

**The campaign ratchet and the claims guard.** The existing "an error cannot become OK by saving" ratchet is the **L6 round-trip invariant** (`test/campaign/invariants.test.ts`:201) — a named list of cases whose fault survives parse → serialize → check — not the golden/repair pair. Commit 2a's serializer change is the most likely thing in this plan to disturb it, so 2a re-runs it and re-records any movement with a reason. The L8 suite adds its own ratchet in the same spirit: a golden verdict may become *more* conservative without ceremony and may never become *less* conservative without an explicit re-record. The claims guard (commit 16) scans every new string and document for the reserved sentence forms; the guard is itself verified by planting a violating sentence in a fixture doc and asserting the test fails. And the CI job that runs `--engine auto` with `SYSPROSE_NO_Z3=1` and asserts exit 2 means the honest-absence path is executed on every push — the single most likely thing to rot into a silent green, exercised continuously.

## 6. Risks, semantic traps and non-goals

### Non-goals (deliberate)

1. **No unbounded proof in TypeScript.** The in-process behaviour engine decides only the finite abstraction it exhaustively explored. Anything unbounded goes to z3 k-induction or to an SMV export, and the report names which.
2. **No event pool, deferred events or PSSM completion events.** `triggerEquals` is an exact match and completion chasing is bounded at 64. The profile prints `deferredEvents: 'none'` and a model needing them gets `verification/behaviour-unsupported-construct`, never a verdict.
3. **No dense time in-process.** `after(n)` is a discrete clock; real-time patterns with sub-tick bounds are export-only.
4. **No liveness in-process.** `existence` and `response` are `inconclusive` until a lasso search lands and a fairness assumption is named.
5. **No reactive realizability.** `consistency` decides satisfiability of static contracts. `katis-2022` and `larraz-tinelli-2022` are about a different question; the word *realizable* is reserved by the claims guard.
6. **No kernel-checked proofs in-process.** z3 is trusted as a solver. The vocabulary is "proved by z3 (negation unsat)", never "kernel-checked" — that phrase is reserved for an imported Lean result whose axiom set was parsed.
7. **No LLM inside the tool.** Property authoring is the agent's job, guided by `#prompt`; the tool supplies the dictionary, the template, gate 0, the four gates and the back-translation. `danso-2026` sets the bar and the gates are the answer to it.
8. **No invented syntax.** Properties, evidence, fault hypotheses and temporal patterns are §7.27 metadata over a shipped `SysproseVerification` package, exactly as `#prompt` is a keyword over `SysproseStatements`. Two of the four keywords put to this plan are refused outright because the standard already expresses them, and one of the two remaining is held (§2.1).
9. **No in-browser solver in this plan.** z3 WASM needs `SharedArrayBuffer`, i.e. COOP/COEP headers GitHub Pages cannot set. The app reads evidence and says "prove in the terminal" with the exact command. The `coi-serviceworker` workaround is a later decision, not a promise.

### The one declared deviation from the standard

**§8.4.17 — a RequirementCheck with a false assumption.** Part 1 §9.2.14.2.8 gives the `RequirementCheck` result as `allTrue(assumptions) implies allTrue(constraints)` (the shipped `Systems Library/Requirements.sysml` spells it with the call parentheses), so a requirement whose assumption is **false** is **true** under the standard's own semantics. This tool reports `vacuous` ⇒ `inconclusive` ⇒ exit 2 instead, because a requirement discharged by an unsatisfiable antecedent tells an engineer nothing and is the classic way a requirement set passes while meaning nothing. **This is a deviation, not an interpretation**, and it is recorded as one in `docs/CONFORMANCE.md` with the clause number beside it. `--strict-vacuity` makes it louder; nothing makes it agree with the standard.

### Semantic traps, and how each is reported

| Trap | How it is handled and said |
|---|---|
| **KerML semantics are under-specified** (`almeida-2024`) | Only single-valued scalar features with ScalarValues typing are encoded. Multiplicity > 1, feature chains through unresolved typings, string and enum comparisons, `null`, `%` and variable exponents are `verification/unsupported-construct` — inconclusive, exit 2, **construct named**. The checker states its own reading in `docs/CONFORMANCE.md`; no report claims to implement the specification's semantics. |
| **No domain axioms from quantity kinds** | The tool derives nothing from ISQ typing: it does **not** know that a power, a mass or a kelvin temperature is non-negative. `cruisePower : ISQ::PowerValue` freed with only an upper bound admits `cruisePower = -1 W`, and the witness re-evaluation gate *confirms* the arithmetic — so a one-sided free variable is `verification/free-variable-unbounded` ⇒ inconclusive, never a refutation. Freeing a feature is a two-sided act. |
| **Units and dimensions** | Everything is scaled to coherent SI through the lifted `ScaleMap`. Ordering on °C is encoded in kelvin (a monotone affine map); arithmetic on °C is **refused**, exactly as the numeric surface refuses it. A dimension clash or an unknown unit reuses the existing refusal sentences. Every verdict line carries the count of relations not encoded. |
| **A plain `constraint` is an obligation** | It has no `requirementRole`, and it is what `checkConstraints` judges. Filing it as an axiom would turn one false constraint into "axioms inconsistent" and downgrade every real violation in the run to inconclusive. The axiom set is exactly feature-value bindings, `bind` equalities and `assert constraint` bodies. |
| **Feature values are bindings, not defaults** | A `=` value is an axiom. `--free F` is the explicit way to release one, and a refutation obtained under `--free` is reported as **`design-admitted`** — "a design the model admits, not a violation of it", exit 2 — never as a violation and never as exit 1. |
| **Vacuity** (`kupferman-vardi-2003`) | Antecedent vacuity is detected (premises unsatisfiable, or false at the values), plus the tautology check, plus the once-per-run axiom-consistency precondition, plus — new — the refinement antecedent check of §3.6 step (0), without which contradictory sub-contracts entail anything. Sub-formula-replacement vacuity for nested `implies` is **not** done. Gate 4 of `property-check` is *syntactic* non-triviality only: a clause the model's own literals already satisfy passes it. Both limits are in the register. |
| **Composition circularity** | Bare-guarantee obligations are unsound under mutual support. Normal form `nf(C) = ¬A ∨ G` is used throughout, per `cimatti-2015`; `cofer-2012`'s soundness argument rests on a temporal order a static check does not have, and the report says so rather than borrowing it. |
| **Bare connections are not equalities; item flows are** | γ is `bind` ∪ the directional item flows `propagateValues` already carries, because a γ that diverged from the tool's own value semantics would break commit 1's gate. Only a bare `connection` with no flow is refused, listed under `notEncoded` with the `bind` hint. Counter-evidence recorded: `cristoforetti-2026` §4.1 maps `connect` and `bind` alike. |
| **Element ids are not stable** | Fresh UUIDs on every load. All digests canonicalise ids to qualified names; all SMT `:named` assertions use qualified names; the byte-stability test runs across two processes. |
| **Nonlinearity** | Products and quotients of free variables give QF_NRA — including the flagship endurance obligation the moment `cruisePower` is freed. nlsat is decidable but may time out → "inconclusive: unknown after T ms" with the bound printed. Never silently retried with a weaker encoding. Division by a free variable adds `≠ 0` **and says so**. |
| **Bounds are not proofs** | "unsat within scope N" is not inconsistency; "no violation within k" is not proof; "no cut set up to order 2" is not absence of failure; "unreachable" is not unreachable when a completion budget was hit. Each is printed with its bound, every time. |
| **A keyword is not a construct** | `#precondition` and `#postcondition` are a third-party spelling of something SysML v2 already has three constructs for. Sysprose reads and preserves them losslessly, lists them under `contracts --keywords` with the words "not SysML v2, not a Sysprose keyword", and lets them contribute to a proof only under `obligations --from-keywords`, whose use is printed on every derived line and recorded in the evidence record's `flags`. |
| **Absence of an annotation is not a fact** | A model with no `#exceptional` anywhere is a model that has not classified its outcomes, not one whose states are all benign. An untagged state is unclassified, never "not a failure". The same rule would govern `#observable` if it ever ships. |
| **Evidence is text, and only Sysprose has been asked to read it** | The digest catches model edits, not hand-edited evidence. And the verdict facet is an unbound tag holding a quoted string: a conforming external reader may ignore it entirely. The Sysprose → other-tool round trip is **untested** until commit 16's interop probe, and no claim is made about it before then. What the tool can do — and does — is flag a `verdict` facet with no carrier as "claimed pass, no evidence", refuse to launder a `fail` into a `pass`, and refuse to write `pass` for a claim that is not `proved`. |

### Expected yield on a real model

Nothing in this lane promises that a real requirement set will be decidable. On `examples/uav-isr.sysml` — the best case that exists, a model written by the same hands as the tool — **0 of 2 guarantees are refused and both are encodable**. That number is not a forecast. A requirement set drawn from a programme will contain prose-only requirements (no formal clause), temporal ones (gate 0 refuses them), °C arithmetic and offset scales (refused), collection-valued and enum comparisons (unsupported-construct), and nonlinear obligations that time out. **A user approving this lane should expect the first honest run on a real model to land a substantial fraction in `no-formal-clause` and `not-encodable`**, and should treat `obligations --missing` as the deliverable that measures it. The first thing to do after commit 2c is to run it on a real requirement set and record the histogram in the ledger; if the encodable fraction is small, that is information about the model *and* about this plan's value, and it arrives before the SMT engine is built rather than after.

### Performance, the gate budget, and licence limits

z3 WASM: **init plus three checks measured once at 343 ms** in a Node 22 process — init alone was not timed separately, and `z3-solver` is not in `node_modules` today, so the figure is re-measured at commit 4 and registered. The WASM asset is tens of megabytes, dynamically imported and excluded from the browser bundle.

**The baseline the budget moves from, measured rather than deferred.** `npx vitest run` at `f1cd587` on this machine: **192.74 s wall clock, 129 files, 2245 tests** (`/usr/bin/time`, one run, the full unit + integration + conformance + campaign suite; `npm run test:e2e` is separate and not in this figure). That number is **machine-dependent** — it is a developer VM, not CI — so it is a baseline to move *from*, not a threshold to defend in the abstract; what is portable is the *ratio*, and every re-measurement is taken on the machine that took the previous one.

**The gate budget, because nobody costed it.** This plan adds, under "full gate on every commit": a differential gate over 81 fixtures + 2 examples, a relation census over the same, a fault-tree enumeration of Σ C(n,k) solver calls, and an explorer defaulting to 10 000 configurations. Vitest runs spec files in **parallel workers**, and each worker that touches z3 pays its own WASM init. Therefore:

- **The wall-clock budget for `npm test` is 192.74 s + 25 % ≈ 241 s**, anchored on the measured baseline above and re-registered at commit 5 with the same command on the same machine. A commit that exceeds it either explains itself in its message or **moves the solver-touching suites behind `npm run test:smt`** — a script the full gate still runs and the per-commit gate may skip. A budget with no baseline and no escape hatch is not a budget; both are now stated, and the escape hatch is the redesign trigger, not a silent slide.
- **Per-suite timeout policy:** every solver-touching suite declares an explicit vitest timeout; no solver call is unbounded; the default per-check timeout is 5000 ms and the fault-tree and explorer bounds are as documented.
- **z3 WASM under worker parallelism is treated as unproven until commit 4 measures it.** Commit 4 runs the SMT suites under the default worker pool and under a single fork, comparing verdicts and wall clock, with `smt.random_seed` fixed so a determinism failure is a real one and not a seed. If the WASM instance turns out not to be worker-safe, the SMT suites are pinned to a single worker and the cost is recorded — a budget decision, not a correctness one.

Core minimisation costs at most one extra check per core member; fault-tree enumeration prints its check count; explicit-state exploration defaults to 10 000 configurations and depth 200 and prints the frontier size when a bound is hit.

External tools: `ocra` and `nuXmv` are free but not open source (FBK licence) and are never bundled; Kind 2 is open; z3 is MIT — recorded in `docs/LICENSES.md`. **Not installed on this machine today:** nuXmv, NuSMV, SPIN, UPPAAL, Kind 2, Alloy, TLA+ tools, **the cvc5 binary** (`which cvc5` finds nothing; the 1.3.4 Python package in `~/.venvs/quant` is invisible to a PATH-and-version probe), and `z3-solver` itself until commit 4. `z3` 5.0.0 **is** on PATH. Every one of those absences is an exit 2 with the files written and the command to run printed.

## 8. Open decisions for the user

**1. Should `--allow-inconclusive` exist at all, and how far should it reach?**
The strict contract (any inconclusive ⇒ exit 2) is what stops a missing solver turning CI green. The flag is an escape hatch for a team that wants a green build while a nonlinear obligation times out. The danger nobody named in review is the flag's **scope**: unscoped, it also forgives a solver that was never installed, and it forgives a real violation that got mislabelled `axioms inconsistent`.
*Recommended default:* **ship the flag, scoped.** It lowers 2 → 0 only for `verification/timeout` and `verification/unsupported-construct`. It never lowers `verification/tool-absent`, never lowers `verification/vacuous`, never lowers `verification/method-not-performed`, never lowers `design-admitted`, and never wins over a violation. The summary prints the inconclusive count first and names which inconclusives were forgiven. Revisit after a month of real use.
**And the flag that is deliberately NOT shipped:** a team wanting a green build over a verification case whose method the tool did not perform would need a separate `--allow-unperformed`. This plan does not ship one, and no commit gate in §4 forgives `verification/method-not-performed`. If you want it, say so and it becomes its own decision — it is not something `--allow-inconclusive` quietly grows into.

**2. Should a `connection` between ports ever be read as an equality?**
The specification does not say it is one, and `propagateValues` does not treat a bare `connect` as one — so the default is to refuse and list it. But `examples/uav-isr.sysml` wires nine connections and zero binds, so a refinement check on the shipped example encodes nothing until the model is edited. **Counter-evidence to weigh:** `cristoforetti-2026` §4.1 — the one published SysML v2 → OCRA path — translates `connect` **and** `bind` alike into OCRA ports and connections, and Cimatti's γ is by definition the connection-and-delegation assertion. So this plan's refusal is a **stricter reading than the published path takes**, not a consensus, and that is the strongest argument for shipping `--connections-as-equalities` rather than only refusing.
*Recommended default:* **keep the refusal as the default and ship the opt-in**, noting that γ already includes item flows so a model wired with `flow` is checkable as-is, and ship `examples/uav-power-budget.sysml` using `bind`. If you would rather the shipped ISR example be checkable, the alternative is to add `bind` statements to it — say the word and that becomes part of commit 10.

**3. z3 as an optional dependency, or a hard one?**
Optional keeps the browser bundle clean and makes the absent path a real tested state. **But the reasoning in the first draft was wrong: npm installs `optionalDependencies` BY DEFAULT**, and skips them only on a platform/engine failure or with `--omit=optional` / `--no-optional`. A fresh `npm ci` *would* have z3-solver, so absence is not the default and must be **forced**.
*Recommended default:* **optional**, with the honest-absence path exercised by the CI job that sets `SYSPROSE_NO_Z3=1` (and, for a genuine no-install check, `npm ci --omit=optional`) — not by imagining that a fresh clone lacks the package.

**4. Which phases do you actually want — and what does each cost?**
The first draft asked this and gave no cost for any answer, so it could not be answered as posed. The estimates below are **commit counts and regression surfaces**, which is what this project actually spends; the phase-0 range is the one to trust least until commit 2a's corpus diff is measured.

| Block | Commits | What is new code vs. changed behaviour | Main risk |
|---|---|---|---|
| **Phase 0** (1, 2a–2d, 3) | 6 code commits, plus the doc-only commit 0 | 3 prerequisite fixes (D1, D2, D4) touching shipped round-trip semantics — **D3 is worked around, not fixed** — 3 new modules, the vocabulary package (a *gap*, not a defect payment), the L8 suite runner | 2a's corpus-wide serializer diff: every golden that moves must be re-recorded with a reason, and the L6 invariant re-run |
| **Phase 1** (4–6) | 3 | z3 bridge + encoder + 2 engines; no behaviour change to existing surfaces | the differential gate or the relation census exposing a real disagreement — which becomes the next commit, not phase 2 |
| **Phase 2** (7–9) | 3 | first writes into user files; +1 validation rule (24 → 25, every count doc moves) | the verdict facet is a compatibility commitment; the "only `proved` writes `pass`" rule must be right the first time |
| **Phase 3** (10–12) | 3 | pure additions over phase 1's solver | soundness of the normal form and of step (0) — the two cases in §5's known-answer corpus are the gate |
| **Phase 4** (13, 14, 14b) | 3 | a refactor of `execute.ts`'s closures + 2 additions | the `execute.ts` refactor is the highest-regression change in the plan; its differential test is what makes it safe |
| **Phase 5** (15–16) | 2 | export/import + the app views + the honesty pass | commit 16 re-measures every count in every doc and adds a new view kind; it is the longest single commit |

*Recommended default:* **commit to phases 0–2 (twelve code commits: 1, 2a–2d, 3–9, plus the doc-only commit 0), then reassess at Checkpoint B.** Phase 3 is the highest-value next block for your domain. Phase 4 answers questions the shipped examples barely pose — a four-state and a three-state trigger-less toy — so it is worth doing *after* you have a model whose modes matter.

**5. Does `#prompt` guidance for property authoring belong in the shipped examples?**
Putting authoring guidance into `examples/uav-isr.sysml` makes the agent loop self-documenting, but it changes the example's element counts, which several tests and docs pin.
*Recommended default:* **a separate `examples/contract-authoring-prompts.sysml`**, so the shipped ISR and vehicle models stay exactly as they are.

**6. Should Sysprose ship the `#exceptional` keyword, and what about `#observable`?**
The specification is genuinely silent on both — "exception" occurs 0 times in Part 1, "observable" twice in one narrative sentence — and §7.27.4's own example (`#situation occurrence def Failure;`) shows a failure marker being user-defined, so shipping is sanctioned. But a shipped `metadata def` the tool writes into user files is a **compatibility commitment**: withdrawing it later turns a user's file into `verification/keyword-names-nothing`.
*Recommended default:* **ship the reader, the resolver and the alias table (commit 2d), ship `#exceptional`, and HOLD `#observable`.** `#exceptional` earns its entry at commit 14b, where it turns a hand-written safety question into an `absence` × `globally` obligation — one of the four patterns the engine can actually decide — with a witness trace and a printed bound. `#observable` discharges nothing; its entire output would be one info verdict and an atom filter, and nothing in this plan depends on it. Its design is written (§3.12) and it is one commit away whenever a shipped example needs it.

**7. If you stop at a checkpoint, what happens to the docs?**
At Checkpoint B the §3 table has twelve rows, and six of them — `refine`, `bounds`, `reach`, `check-behaviour`, `fault-tree`, and `export` / `certificate-import` — do not exist. `docs/CLI-REFERENCE.md` is generated from the spec table, so it stays honest on its own; the README capability table and `docs/USER-GUIDE.md` are prose and would not. **The clean-stop pass:** delete the unshipped rows from the §3 table into a short "Not built" list at the end of §3, with the commit numbers that would build them; regenerate `docs/CLI-REFERENCE.md`; trim the README capability table and the USER-GUIDE sections to what `COMMANDS` actually holds — both are guarded, so `readme.test.ts`:315 and `user-guide.test.ts`:226 fail loudly if you do not; mark the unshipped `verification/*` codes as reserved-not-emitted in `docs/DIAGNOSTIC-CODES.md`; and record the stop point and the reason in the ledger.
*Recommended default:* **budget one commit for the clean-stop pass at whichever checkpoint you stop at**, and treat it as part of stopping, not as optional tidying. A plan that advertises six tools it does not have is the same defect this document exists to prevent, arriving through the back door.
